# Day 25: Triggers — Full Notes and Theory

---

## 1. What Triggers Are and When to Use Them

A **trigger** is a PL/SQL block that runs **automatically** when a specified DML event (INSERT, UPDATE, DELETE) occurs on a table. Use triggers for audit trails, defaulting or validating column values, and enforcing rules that go beyond simple constraints. Overuse can make behavior hard to trace; prefer constraints and application logic when they suffice. All examples use **hr.employees** and **hr.departments** (or copy tables where altering HR is not allowed).

- **BEFORE** — runs before the row(s) are modified; you can change :NEW values (INSERT/UPDATE).
- **AFTER** — runs after the row(s) are modified; you can read :NEW and :OLD.
- **Row-level (FOR EACH ROW)** — runs once per row; you have :NEW and :OLD.
- **Statement-level** — runs once per statement; no :NEW/:OLD.

---

## 2. BEFORE and AFTER; Row vs Statement

- **BEFORE row:** Use to set or validate :NEW.column (e.g. default department_id, prevent salary decrease).
- **AFTER row:** Use to audit or sync other tables (e.g. insert into audit table).
- **Statement-level:** Use when you need to run logic once per INSERT/UPDATE/DELETE statement (e.g. log “batch inserted”). No :NEW/:OLD; use **INSERTING**, **UPDATING**, **DELETING** to know the triggering event.

---

## 3. NEW and OLD (Row-Level Triggers)

In a **FOR EACH ROW** trigger:

- **:NEW** — the new row (INSERT or UPDATE). In BEFORE triggers you can assign :NEW.column := value. In AFTER, :NEW is read-only (already written).
- **:OLD** — the old row (UPDATE or DELETE). Read-only.

INSERT has only :NEW. DELETE has only :OLD. UPDATE has both. Use colon prefix in the trigger body (:NEW.salary, :OLD.salary).

---

## 4. Trigger to Audit Salary Changes on hr.employees

Create an audit table, then an **AFTER UPDATE OF salary** row trigger that logs employee_id, old and new salary, and date:

```sql
CREATE TABLE emp_salary_audit (
  audit_id     NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  employee_id  NUMBER(6),
  old_salary   NUMBER(8,2),
  new_salary   NUMBER(8,2),
  changed_date DATE DEFAULT SYSDATE
);

CREATE OR REPLACE TRIGGER trg_emp_sal_audit
AFTER UPDATE OF salary ON hr.employees
FOR EACH ROW
WHEN (OLD.salary != NEW.salary)
BEGIN
  INSERT INTO emp_salary_audit (employee_id, old_salary, new_salary)
  VALUES (:NEW.employee_id, :OLD.salary, :NEW.salary);
END;
/
```

**WHEN (OLD.salary != NEW.salary)** avoids firing when salary was not actually changed. Use **OF salary** so the trigger runs only when the salary column is updated.

---

## 5. Trigger to Validate department_id on INSERT

**BEFORE INSERT OR UPDATE OF department_id** to ensure department_id exists in **hr.departments** (or rely on FK; this illustrates the pattern):

```sql
CREATE OR REPLACE TRIGGER trg_emp_dept_check
BEFORE INSERT OR UPDATE OF department_id ON hr.employees
FOR EACH ROW
WHEN (NEW.department_id IS NOT NULL)
DECLARE
  v_count NUMBER;
BEGIN
  SELECT COUNT(*) INTO v_count
  FROM hr.departments
  WHERE department_id = :NEW.department_id;
  IF v_count = 0 THEN
    RAISE_APPLICATION_ERROR(-20002, 'Invalid department_id: ' || :NEW.department_id);
  END IF;
END;
/
```

In BEFORE triggers you can use **WHEN (NEW.column ...)** to restrict when the trigger runs.

---

## 6. Mutating Table Considerations

A **mutating table** is the table being modified by the DML. In a **row-level** trigger you **cannot** query or modify the same table (e.g. SELECT FROM hr.employees inside a trigger on hr.employees). Doing so can raise **ORA-04091: table is mutating**. Use one of:

- **Statement-level** trigger (no FOR EACH ROW) to query the table after all rows are modified.
- Store row data in a package collection and process in an **AFTER STATEMENT** trigger.
- Query or update **another** table (e.g. audit table) in the row trigger.

---

## 7. When to Use Triggers

- **Use for:** Audit trails (who/what/when), defaulting columns (e.g. :NEW.department_id := 50), validating against other tables or complex rules.
- **Prefer constraints** for uniqueness, NOT NULL, check, and foreign key. Prefer application code when logic is complex or needs to be testable outside the DB.
- Document triggers; they run implicitly and can make debugging harder.

---

## 8. Best Practices and Summary

- Use **WHEN** to avoid unnecessary execution (e.g. WHEN (OLD.salary != NEW.salary)).
- Use **OF column** for UPDATE triggers when only specific columns should fire the trigger.
- Avoid mutating table: do not read/write the triggering table in a row trigger; use statement trigger or another table.
- Prefer a **copy table** (e.g. hr_emp_backup) for practice so you do not alter production hr.employees.

**Summary:** Triggers run on DML events; use BEFORE for defaults/validation, AFTER for audit. Use :NEW and :OLD in row triggers; avoid querying the same table in a row trigger. Apply these patterns to hr.employees and hr.departments (or copies) for audit and validation.
